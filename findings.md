# Выводы

Здесь я записываю, что узнал о работе HTTP и API по ходу сценариев.

## Сценарий 01: GET

- В HTTP/2 у запроса нет строки вида `GET /posts/1 HTTP/1.1`: вместо неё в заголовках идут псевдозаголовки `:method`, `:authority`, `:scheme` и `:path`.
- Часть заголовков запроса добавляет сам браузер (`sec-ch-ua`, `sec-fetch-*`, `upgrade-insecure-requests`). Запрос из адресной строки отличается от запроса, который отправляет приложение или Postman.
- Сервер ответил кодом `200` и телом в JSON с полями `userId`, `id`, `title`, `body`. Тип ответа указан в `content-type: application/json; charset=utf-8`.
- Тело передано в сжатом виде (`content-encoding: zstd`): браузер заявил поддержку в `accept-encoding`, сервер выбрал формат. В Fiddler на проводе 192 B, в Inspector виден уже разжатый JSON.
- Ответ отдан из кеша Cloudflare (`cf-cache-status: HIT`, `age`, `cfOrigin;dur=0`), а не напрямую от сервера API. Поэтому время ответа зависит от кеша.
- Из 193.61 мс общего времени подключение (DNS, TCP, TLS) заняло 135.58 мс, сам запрос 24.69 мс, ответ 33.34 мс. Установка соединения дороже, чем получение данных.
- Помимо нужного запроса Chrome сам отправил запрос за `favicon.ico` и создал туннели `CONNECT`. Без фильтра по хосту в списке сессий много лишнего.
- Открытый вопрос: в Overview размер тела ответа 201 B, а в HTTP Inspector 192 B. Причину не выяснил.

## Сценарий 02: POST

- Composer позволяет собрать запрос вручную. Fiddler сам добавляет `Host`, `User-Agent`, `Content-Type` и `Content-Length`; выбор типа JSON на вкладке Body выставляет `Content-Type: application/json`, повторно добавлять его вручную не нужно.
- Ответ `201 Created` и заголовок `location` указывают, где «создан» ресурс (`/posts/101`), но JSONPlaceholder только имитирует создание: после POST запрос `GET /posts/101` возвращает пустое тело `{}` и код `404`.
- Сервер вернул отправленные поля и добавил `id: 101`. Идентификатор присваивает сервер, клиент его не передаёт.
- Ответ на POST пришёл не из кеша (`cf-cache-status: DYNAMIC`) и занял 328.77 мс, а ответ на GET из кеша 33.34 мс. Время ответа сильно зависит от кеша.
- При повторной отправке того же POST время обращения к серверу изменилось (`cfOrigin;dur` 265 мс и 108 мс). Одного замера недостаточно, чтобы делать выводы о скорости.
- Запрос из Composer отправляет сам Fiddler (процесс `fiddler.webui`): в нём нет браузерных заголовков и `Accept-Encoding`, поэтому ответ пришёл без сжатия.
- Открытый вопрос: в Overview размер тела запроса 0 B, хотя `Content-Length` равен 102. Причину не выяснил.

## Сценарий 03: Breakpoint

- В Fiddler Everywhere точка останова делается через вкладку Rules: действие Set Request Breakpoint. Правило работает, только когда включены и общий переключатель Rules, и само правило, и только для нового трафика.
- Приостановленный запрос в таблице заголовков не редактируется. Менять его можно через вкладку Raw (первая строка запроса), а отпускать нажатием на метку PAUSED.
- Пока запрос удерживается, браузер не ждёт вечно: он оборвал соединение (`ERR_CONNECTION_CLOSED`) и сам отправил запрос заново. В списке накопились несколько приостановленных сессий, и каждую пришлось возобновлять. Менять запрос нужно быстро.
- После замены `/posts/1` на `/posts/9999` сервер вернул `404` и пустое тело (2 B). Этот ответ тоже пришёл из кеша Cloudflare (`HIT`): кешируются и ошибки.
- Время удержания входит в тайминги сессии: Breakpoint занял 2.63 мин, хотя ответ сервера пришёл за 198.46 мс. По таким замерам нельзя судить о скорости сервера.

## Сценарий 04: подмена ответа

- Аналог AutoResponder в Fiddler Everywhere это правило с действием Return File (или Return Manual Response). Подмену отличить просто: Remote HTTP Version `HTTP/1.1` при клиентском HTTP/2, длительность 1–7 мс, в ответе только те заголовки, что записаны в файле (2 вместо 23).
- Поле ручного ввода Return Manual Response слепляет переводы строк: заголовки и тело сливаются в одну строку, Fiddler дописывает лишний `Content-Length`, тело теряется. Файл ответа (`.dat`) с переводами строк в стиле Windows работает правильно.
- Если Fiddler не находит выбранный файл, он сам отвечает кодом `404` и коротким телом (512 B). Это легко принять за ответ сервера, поэтому файл лучше хранить в простой папке.
- В новом правиле в условии стоит заготовка `http://www.example.com/`. Пока она не заменена, правило ни на что не реагирует и запросы идут к настоящему серверу.
- В колонке Remote IP у подменённых сессий всё равно виден адрес сервера, хотя ответ сформировал Fiddler.
- Правила не затрагивают сопутствующие запросы Chrome, например `/favicon.ico`: он приходит с настоящего сервера.

## Сценарий 05: время ответа

- Установка нового соединения занимает около 120–135 мс (DNS, TCP, TLS), сам запрос и ответ в кешируемом случае меньше. Для GET из кеша: подключение 135.58 мс, запрос 24.69 мс, ответ 33.34 мс.
- Ответ из кеша Cloudflare пришёл за 33.34 мс, ответ POST от сервера за 328.77 мс. Разница в десять раз объясняется кешем, а не размером данных.
- Для маленьких ответов TTFB и TTLB почти не отличаются (32.61 и 33.18 мс, 375.66 и 376.70 мс): скачивание тела занимает доли миллисекунды.
- Во Fiddler время «с Fiddler» заметно больше, чем «без Fiddler» (193.61 и 103.85 мс у GET из браузера): добавляются шаги перехвата HTTPS (получение сертификата 50.38 мс, рукопожатие с клиентом 12.26 мс). У запроса из Composer эти шаги равны 0 мс.
- Время удержания на breakpoint или подмена ответа искажают замер: подменённые ответы приходят за миллисекунды, а удержание запроса занимает минуты.

## Общие наблюдения

- Чтобы видеть HTTPS-трафик, в Fiddler нужно включить расшифровку и установить сертификат.
- Фильтр по хосту сильно упрощает работу со списком сессий.
- Запросы из браузера и запросы из Composer различаются заголовками, поэтому сравнивать их напрямую нужно с учётом этого.
- Правила Fiddler действуют только на новый трафик: после включения правила запрос нужно отправить заново, а лучше из нового окна браузера, открытого кнопкой Browser.
