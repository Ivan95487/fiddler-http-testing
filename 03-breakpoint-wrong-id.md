# Сценарий 03: изменить запрос на лету (неверный ID)

**Цель:** остановить запрос браузера до отправки на сервер, изменить в нём ID поста и посмотреть, как отреагирует сервер.

**Инструмент Fiddler:** Rules → Set Request Breakpoint, вкладка Raw в HTTP Inspector (Fiddler Everywhere)

**Запрос:** `GET https://jsonplaceholder.typicode.com/posts/1` → заменяем на `/posts/9999`

## Предусловия

- Fiddler запущен и перехватывает трафик.
- Запрос отправляется из браузера, открытого через кнопку **Browser** во Fiddler (или из нового окна, запущенного после включения правила). Точка останова работает только для новых соединений и новых запросов.

## Шаги

1. Открыть вкладку **Rules** и нажать **Add Rule**.
2. Название правила: `Breakpoint posts/1`. Условие: **URL — Contains — `jsonplaceholder.typicode.com/posts/1`**.
3. Действие: **Set Request Breakpoint**. Галочку «Stop processing more rules» не ставить. Нажать **Save**.
4. Включить переключатель вкладки Rules и само правило.
5. Очистить список сессий и открыть в браузере `https://jsonplaceholder.typicode.com/posts/1`. Страница не загружается: запрос удерживается Fiddler.
6. В Live Traffic найти сессию с иконкой паузы (в колонке кода ответа прочерк). В HTTP Inspector у запроса стоит метка **PAUSED**, а ответ пустой.
7. Открыть вкладку **Raw** у запроса и в первой строке заменить `/posts/1` на `/posts/9999`. Таблица заголовков в приостановленном запросе не редактируется, менять можно только через Raw.
8. Нажать на метку **PAUSED**: запрос уходит на сервер уже с изменённым путём.
9. Посмотреть ответ в нижней части Inspector: код, заголовки и тело.
10. Выключить правило, чтобы оно не останавливало следующие запросы.

## Ожидаемый результат

- Сервер не находит пост с ID 9999 и возвращает `404` с пустым телом.
- Запрос, который ушёл на сервер, отличается от запроса, который отправил браузер: путь изменён в Fiddler.

## Фактический результат

- **Исходный запрос браузера:** `GET /posts/1`
- **Запрос после изменения (вкладка Raw):** `GET https://jsonplaceholder.typicode.com/posts/9999 HTTP/2`
- **Код ответа:** `404`
- **Заголовок Content-Type:** `application/json; charset=utf-8`
- **Размер тела ответа:** 2 B (`content-length: 2`), как у пустого объекта `{}` из сценария 02
- **Заголовки ответа:** 22 заголовка; `cf-cache-status: HIT`, `cfOrigin;dur=0`, `server: cloudflare`, `x-powered-by: Express`
- **Что заметил интересного:**
  - Приостановленный запрос можно менять только через вкладку Raw, а не в таблице заголовков.
  - Пока запрос удерживался, браузер не дождался ответа и сам повторял его: в списке появилось несколько приостановленных сессий с одним адресом, каждую пришлось возобновлять отдельно. Для проверки нужно менять запрос быстро.
  - Браузер показал ошибку «Не удаётся получить доступ к сайту» (`ERR_CONNECTION_CLOSED`): запрос удерживался слишком долго, браузер разорвал соединение, и ответ `404` увидел только Fiddler. Чтобы страница показала результат, запрос нужно изменить и отпустить быстро.
  - Время удержания запроса попало в тайминги (вкладка Overview): Breakpoint занял 2.63 мин, общее время 2.64 мин, хотя ответ сервера занял 198.46 мс (TTFB 241.01 мс, без учёта Fiddler 460.03 мс). Тайминги запросов с точкой останова нельзя использовать для оценки скорости сервера.
  - Ответ `404` для несуществующего поста тоже пришёл из кеша Cloudflare (`HIT`), то есть кешируются и ошибки.
  - В Raw запрос записан с полным URL в первой строке (`GET https://… HTTP/2`), а не только с путём.
- **Статус:** Pass
